## Deliverable 1 — Executive Verdict

**READY WITH REQUIRED PLAN CHANGES.**

This pass found something more architecturally significant than either prior pass: **`payload.locators` — a full ranked array of Master-DOM-derived candidate selector strings, not just an identity descriptor — is generated by `LocatorIntelligenceEngine` running inside the injected Master browser script, and attached to the outgoing interaction payload unconditionally (not feature-flag-gated at the point of assignment) for every `CLICK`/`DOUBLE_CLICK`/`DRAG`/`INPUT`.** This is a larger-scale version of the INV-1 violation the first two passes described only in terms of a single legacy `selector` field. The target architecture (Deliverable 1 of the first package) is unaffected — SID-only wire transmission is still the correct target — but Deliverable 2's disposition table materially mischaracterized where candidate generation happens today: it is Master-side and transmitted wholesale, not Slave-side as the first plan assumed when it said "keep, re-point at the SID-only contract" for `CandidateGenerator`/`RankingEngine`/etc.

Everything else confirmed in this pass (the real composition root, the actual default execution path, the shadow-mode mechanism, the terminal-error contract) sharpens rather than contradicts the second pass's findings. Full detail below.

## Deliverable 3 — Newly Discovered Work

1. **[Major] Candidate-list generation location correction.** `LocatorIntelligenceEngine` runs Master-side (inside the injected `InteractionRecognizer`), producing `resolution.locators` (a ranked array of Master-DOM-derived selector strings) and `resolution.identityDocument` (EID), both attached unconditionally to `payload.locators` / `payload.identityDocument` for every captured `CLICK`/`DOUBLE_CLICK`/`DRAG`/`INPUT` — see Deliverable 2 row 1. This requires a genuinely new phase of work: **moving candidate generation to the Slave**, not just splitting the EID's `cssSelector` field as the first plan's Task A1 assumed. This is bigger than Task A1 — it's a new task, LI-MIG-A0 (see Deliverable 6).

2. **RKP `stageName` mismatch verification.** Confirm whether `rkp/TelemetryAdapter.mjs`'s `'RESOLUTION'`/`'EVALUATION'` string match against `ev.stageName` currently ever succeeds against real telemetry (it may already be dead code / a latent bug predating this migration). New task, low urgency but cheap to check, and directly relevant to Deliverable 2 row 4.

3. **`LI_SERIALIZE_FEATURES` interaction with `payload.locators`/`payload.identityDocument` population, unresolved.** `LocatorSerializer.mjs` checks `featureFlags.isEnabled('LI_SERIALIZE_FEATURES')` (default `false`, since it depends on `LI_IDENTITY_DOCUMENT` which is also default `false`) to decide whether to include "features"/EID in its serialized output. Whether this actually strips or nulls `payload.locators`/`payload.identityDocument` in the default-flags case, or only affects a separate `metadata.features` field, was **not traced to a conclusion in this pass** — `UNKNOWN — REQUIRES REPOSITORY VERIFICATION`: read `LocatorIntelligenceEngine.process()`'s full body and confirm whether it calls `LocatorSerializer` internally and what it returns for `resolution.locators` when `LI_SERIALIZE_FEATURES` is off. This directly affects Task 0.3 (flag-state verification) and the severity of the Deliverable-3-item-1 finding — if the candidate list is empty/stripped by default, the wire-level exposure is smaller in practice than the code path suggests in the worst case, though `ActionDispatcher`'s assignment of `payload.locators = resolution.locators` itself is still unconditional.

4. **Enumerate `sequences/` files that use `payload.selector`-style step definitions**, to size Task C0's actual migration/exemption effort (referenced as `UNKNOWN` in the v2 doc, still not enumerated in this pass — genuinely new work, not yet started).

5. **`ActionSimulator.mjs`'s terminal/fatal error contract must be preserved by any new component.** The chunk-runner (`LocatorResolver.mjs` lines 690–718) and the legacy retry loop (lines 754–767) both hardcode the same list of "fatal, do not retry" error types/codes: `ConfidenceGateRejectionError`, `ConfidenceBelowThresholdError`/`LF-602`, `GlobalTimeoutError`, `QueueDeadlineExceededError`, `LF-504`, `LF-702`, `ContractViolationError`/`LF-701`, `MaxAttemptsReachedError`, `LF-505`, `RecoveryExhaustedError`, `LF-605`, `AmbiguousResolutionError`/`LF-603`, `VerificationMismatchError`/`LF-601`. Any new SID-resolution error path (Phase A/B) or new `BehavioralVerificationEngine` failure (Phase C.5) must throw one of these existing types/codes, or be explicitly added to **both** hardcoded lists — not previously called out as a discrete task.

6. **Reuse `LI_SHADOW_MODE`, don't reinvent it** — see Deliverable 2 row 5. This removes a chunk of previously-planned new work (v2's implicit assumption that shadow/parity testing needed to be built).

### Phase A — corrected/extended

**Task LI-MIG-A0 (new, precedes A1) — Move candidate generation from Master to Slave.**
- **Objective:** address Deliverable 3 item 1 — the actual core architectural violation, larger in scope than the original Task A1 (EID field split) assumed.
- **Files:** `src/browser/execution/ActionDispatcher.mjs` (specifically the injected `InteractionRecognizer.emit()` method, lines ~349–361 confirmed this pass), `src/browser/execution/locatorIntelligence/engine/LocatorIntelligenceEngine.mjs`, and its full dependency chain (`FeatureExtractor`, `IdentityDocumentBuilder`, `CandidateGenerator`, `CandidateDeduplicator`, `StructuralAnalyzer`, `RankingEngine`/`AdditiveRankingEngine`, generation `strategies/*` — confirmed present, not re-verified line-by-line for Master-DOM-specific assumptions in this pass).
- **Current behavior:** on the Master, for `CLICK`/`DOUBLE_CLICK`/`DRAG`/`INPUT`, `new LocatorIntelligenceEngine().process(data.target, data.composedPath)` runs against the Master's live DOM, returns `{ locators, metadata, shadowPath, identityDocument }`; all four are attached to the outgoing `payload` unconditionally.
- **Required change:** `ActionDispatcher`'s `InteractionRecognizer.emit()` must stop calling `LocatorIntelligenceEngine.process()` against the Master DOM for candidate generation. It should instead capture and transmit **only** the SID-equivalent identity signal (whatever subset of `identityDocument` survives Task A1's split) — no `locators` array, no Master-derived selector strings of any kind.
- **New behavior:** candidate generation (the `FeatureExtractor → CandidateGenerator → ... → RankingEngine` chain) must run **on the Slave**, inside (or called from) `LocatorResolver.mjs`'s composition point, against the Slave's live DOM, using the transmitted SID as input instead of re-deriving from a Master-side DOM node.
- **Dependencies:** must land before or alongside Task A1 (EID split) — they're two views of the same underlying change; consider merging A0 and A1 into one PR/commit in practice even though they're tracked as separate tasks here for clarity.
- **Consumers affected:** `ActionSimulator.mjs` line 32 (`const locators = command.payload.locators || []`) must change to construct candidates via a Slave-side call instead of reading them off the payload; `LocatorResolver.resolve(page, candidates, ...)`'s second parameter changes from "candidates read off the wire" to "candidates generated locally."
- **Interface/data changes:** `payload.locators`, `payload.locatorMetadata`, `payload.shadowPath` (as currently populated Master-side) are removed from the wire contract; `payload.sid` (post-A1) is added.
- **Tests:** parity test — for a fixed fixture set, confirm Slave-generated candidates (post-A0) produce equivalent top-candidate identification to today's Master-generated-and-transmitted candidates, before removing the old path.
- **Completion criteria:** `ActionDispatcher`'s injected script contains no call to `LocatorIntelligenceEngine` (or any of its dependency chain) for candidate generation; `payload.locators` is never populated by `ActionDispatcher`.
- **Rollback:** flag-gated exactly like Phase A/B/E elsewhere in this plan — `featureFlags`/`FeatureFlagManager` governs which side generates candidates during the transition window.

**Task LI-MIG-A1 (revised from first plan) — Split `ElementIdentityDocument`.**
- Unchanged in mechanics from the first plan, but its scope is now understood to be **necessary but not sufficient** — A0 is the larger companion task. Keep A1's original acceptance criteria (no selector-shaped field in the transmittable shape).

- **Objective:** once A0 lands (candidates generated Slave-side), gate whether candidate generation uses the new SID-driven path or (during the compatibility window) still accepts a transmitted candidate list for rollback safety.
- **Files:** `src/browser/execution/LocatorResolver.mjs`.
- **Exact composition, confirmed this pass (811 lines, read in full):**

  - `_resolveInternal()` (line 174) — ingress fast-fail (`V3_SCHEMA_ENFORCEMENT_MODE`), URL-mismatch abort (`[LF-605]`), telemetry (`stageSequence: 11`, `stageName: 'NAVIGATION_EPOCH_GATING'`), builds `ResolutionContext` per candidate, defines `resolveAttempt()` (the actual per-cycle logic, line 238) containing, **in this order**: ResolutionMemory cache check (`LI_RESOLUTION_MEMORY`) → SceneGraph query (`SCENE_GRAPH_ENABLED`) → InferenceEngine (`INFERENCE_ENGINE_V2`/`LI_INFERENCE_ENGINE_V2`) → BatchResolver (`LI_BATCH_RESOLVER`) → **Sequential Pass (lines 564–720, not flag-gated — this is the actual default path)**, which chunks candidates in groups of 3, races them via `Promise`, and classifies errors as fatal/non-fatal per the list in Deliverable 3 item 5.

- **Acceptance criteria:** flag-off behavior byte-identical to pre-migration baseline (verified against the Sequential Pass specifically, since that's the actual default, not the more exotic BatchResolver/SceneGraph/Inference paths which are already opt-in today and unaffected either way).
